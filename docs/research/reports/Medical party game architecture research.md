# Medical party game architecture research

> Question: Research how to design and engineer an online multiplayer party game that feels like "Quiplash meets Pictionary" (Jackbox-style: a shared host screen plus phones as controllers) for people in medical fields (med students, nursing students, nurses, doctors, PAs, dentists). It has to run well in mobile phone browsers, be easy to set up, and resist Zoom-bombing (room code plus optional password, host controls, kick/ban). The humor should poke fun at medicine itself (wordplay, fill-in-the-blank, drawing anatomy or what a nerve does, medical history memes, real healthcare-worker moments, would-you-rathers, survival-style trivia elimination), never at patients. Specifically research: (1) Jackbox Quiplash / Drawful / Fibbage design: round structure, prompt writing craft, voting and scoring, timers, pacing, audience mode, what makes prompts funny, and benchmarks for what makes Quiplash work; (2) the best realtime architecture for a Next.js app deployed on Vercel (Vercel serverless can't hold WebSockets, so compare PartyKit/Cloudflare Durable Objects, Liveblocks, Ably, Pusher, Supabase Realtime, Socket.io on a separate host) for low latency, server-authoritative timers, reconnection, and free-tier cost; (3) smooth mobile-browser drawing canvas techniques (pointer events, touch-action, coalesced events, stroke smoothing, compact stroke serialization, iOS Safari quirks, preventing scroll and zoom); (4) secure room joining and anti-trolling patterns (short unguessable room codes, rate limiting, profanity filters, host moderation, kick/lock lobby); (5) medical humor and educational party games already on the market (e.g., medical Cards Against Humanity–style games, med school trivia apps), how to keep medical humor inclusive and non-stigmatizing toward patients, and fun medical history facts (bloodletting, leeches, trepanation, radium, tobacco smoke enemas) suitable as prompt material; (6) bubbly, squishy, rounded UI/motion design for game buttons (squash-and-stretch springs, haptics via the Vibration API, sound), plus performance and accessibility on mobile.

## Summary

Jackbox's own documentation gives a clear template for the game loop. There are 3 to 8 core players who write or draw. Two answers go head-to-head on each prompt and everyone votes. Anyone past 8 joins an audience tier that votes but, in most Quiplash versions, does not write, and that tier has scaled to 10,000 people. For realtime play, hosted PartyKit shut down on 23 October 2026, so today the natural choice on Vercel is a self-hosted PartyServer Worker on Cloudflare Durable Objects. Each game room gets its own isolated Durable Object, and server-authoritative timers run on Durable Object alarms through onAlarm(). For smooth drawing on phones, the evidence supports perfect-freehand outlines fed by Pointer Events with pointer capture, touch-action: none set on the canvas before any gesture starts, and getCoalescedEvents() for extra points. That last one needs a fallback when it is missing or returns an empty array (older iOS, Firefox Android). On Zoom-bombing, a room code plus password is necessary but not enough. Peer-reviewed data shows 70-82% of zoombombing calls come from insiders who simply share the credentials. So the game also needs host-side controls modeled on Jackbox: hiding the room code, locking the lobby, kick/ban, a tiered filter that rejects bad input and asks for a retype, and moderator removal of content before it reaches the shared screen.

## Verified findings

### Core lobby structure: 3-8 active players who write or draw, plus a separate audience tier that votes and changes scores but usually cannot submit text. Audience mode can scale to very large numbers (Quiplash advertised up to 10,000). Jackbox recommends rotating overflow players into the core group.

- Confidence: **high** · Vote: 3-0 (5 merged claims, all 3-0)
- Evidence: The PlayStation Blog launch post says 'Quiplash is played by 3-8 core players, and works with or without an Audience' and 'up to 10,000 participants'. Jackbox's help page says 'most of our games are suitable for 3-8 players', sends overflow to the audience, and 'strongly recommend[s] rotating in new players'. Jackbox's comparison table shows the Quiplash, Quiplash XL and Quiplash 3 audiences can vote but not submit text. Only Quiplash 2 allows audience text, and only with Audience Play-Along enabled. Verifiers also checked these figures against Jackbox store pages and 2015 coverage by Destructoid and Engadget. The 10,000 figure is a ceiling that is rarely reached. Design implication: cap writers and drawers at 8 and send everyone else to a voting-only audience.
- Sources: https://blog.playstation.com/2015/06/30/quiplash-new-party-game-expands-audience-participation-to-10000/, https://www.jackboxgames.com/how-audience-play-along-differs-in-each-jackbox-game

### Core Quiplash mechanic: two players' answers to the same prompt face off, the other players and the audience vote, and the answer with the most votes wins. Audience votes count toward points. Later versions appear to weight them less than player votes.

- Confidence: **high** · Vote: 3-0
- Evidence: Quote: 'The player whose answer receives the most votes, wins.' The post also says the audience 'actually affects the outcome of the game by voting'. The verifier noted that independent write-ups describe the mechanic the same way across Quiplash 3 and XL, and that audience votes may count for less (for example, Super Quiplash needs 90% of the audience). The verifier could not confirm exactly how audience votes are weighted.
- Sources: https://blog.playstation.com/2015/06/30/quiplash-new-party-game-expands-audience-participation-to-10000/

### Anti-trolling features in shipped Jackbox games (Party Pack 7 and later), which serve as a benchmark: passworded rooms on top of the room code, hiding the room code until the host is ready, starting the game from the controller only, optional platform login, a separate moderator web interface for removing content before it appears on screen, and a tiered profanity/hate-speech filter (None/Moderate/Strict). The filter rejects flagged words when they are typed and asks the player to enter something else; it does not mask them.

- Confidence: **high** · Vote: 3-0 (4 merged claims, all 3-0)
- Evidence: Party Pack 8 post: 'Create a unique password to give to your most trusted players and keep the riff raff out'; 'Hide the room code until you're ready for your audience to see it'; 'Allow moderators to log in via mod.jackboxgames.com to remo[ve] unsavory content before it hits the screen'; 'Prevent users from submitting words that include profanity or hate-speech.' Support article: the filter 'rejects certain words or phrases when they are entered and gives the player who typed them an opportunity to enter something else.' A later Jackbox post (Nov 2022) confirms the None/Moderate/Strict tiers. Moderate blocks hate speech but allows profanity. Design implication: give the host a lobby lock, hidden-code mode, a filter level and a pre-display veto.
- Sources: https://www.jackboxgames.com/streaming-moderation-accessibility-features-jackbox-party-pack-eight/, https://support.jackboxgames.com/hc/en-us/articles/15794794632983-How-does-Profanity-Filtering-work

### Room codes and passwords alone do not stop coordinated trolling. Most zoombombing calls come from insiders with legitimate access (70% on 4chan, 82% on Twitter) who share the credentials. Insiders also tell attackers to use real participants' names, which defeats waiting rooms and manual vetting by name. So the defenses have to be host-side and work during the game (kick/ban, lobby lock once the game starts, a pre-display content veto, identity that is harder to spoof than a display name), not only better join secrets.

- Confidence: **medium** · Vote: 3-0 (2 merged claims)
- Evidence: Ling et al., 'A First Look at Zoombombing' (IEEE S&P 2021): 'Most calls for zoombombing come from insiders who have legitimate access to the meetings (70% on 4chan and 82% on Twitter)... makes passwords ineffective'; 'insiders often share additional information with potential attackers, for example instructing them to select names that correspond to legitimate participants.' This is a single peer-reviewed source with about 200 public attack calls from Jan-Jul 2020. Applying it to game lobbies is an inference.
- Sources: https://arxiv.org/pdf/2009.03822

### Realtime backend: hosted PartyKit is gone. Deploys stopped 16 Oct 2026 and the platform shut down 23 Oct 2026. Its successor, PartyServer, is the realistic way to keep that programming model. PartyServer is a library on Cloudflare Durable Objects in your own account. It provides room-based routing, connection and request lifecycle hooks, broadcasting, and one API for hibernated and non-hibernated objects, and it still works with the partysocket client. Each room runs in its own isolated Durable Object, which fits one authoritative server per game room. Server-authoritative phase timers should use Durable Object alarms through onAlarm(), set with this.ctx.storage.setAlarm(Date). Do not override alarm(), webSocketMessage, webSocketClose or webSocketError.

- Confidence: **high** · Vote: 3-0 (4 merged claims)
- Evidence: PartyKit docs banner: 'The hosted PartyKit platform is shutting down. Deploys stop on 16 October and the platform shuts down on 23 October 2026.' The migration guide confirms that `npx partykit deploy` stops working and that the path forward is replacing partykit.json with wrangler.jsonc and running `wrangler deploy`. Docs: 'Each Party (the server) runs in a separate Durable Object, and is fully isolated.' PartyServer README: '`onAlarm()` - Called when an alarm is triggered... `this.ctx.storage.setAlarm(Date)`' and 'You should not implement/override [alarm()] yourself.' PartyServer is still maintained: latest version 0.5.10, registry updated Aug 2026. Durable Objects have been on Cloudflare's free plan since April 2025. The Vercel-hosted Next.js app stays the frontend, and the Worker hosts the WebSockets.
- Sources: https://docs.partykit.io/how-partykit-works/, https://docs.partykit.io/guides/migrate-to-partyserver/, https://cdn.jsdelivr.net/npm/partyserver@0.5.6/README.md

### Drawing stroke rendering: perfect-freehand's getStroke(points, options) takes [x, y] or [x, y, pressure] points (or {x, y, pressure} objects) and returns a polygon outline. The app renders that outline itself, through getSvgPathFromStroke into an SVG path or a Canvas Path2D. Defaults are size 8, thinning 0.5, smoothing 0.5 and streamline 0.5. simulatePressure is on by default and estimates pressure from pointer speed, so finger strokes on phones vary in width without real pressure data. The README's input pattern: setPointerCapture on pointerdown, add points on pointermove only while e.buttons === 1, and set touchAction: 'none' on the drawing surface.

- Confidence: **high** · Vote: 3-0 / 2-1 (3 merged claims)
- Evidence: README: getStroke 'will return a new array of outline points that will form a polygon'. The options table lists size 8, thinning .5, smoothing .5, streamline .5 and simulatePressure true ('simulate pressure based on velocity'). The React example calls e.target.setPointerCapture(e.pointerId), checks `if (e.buttons !== 1) return`, and sets style={{ touchAction: 'none' }}. The defaults claim passed 2-1 because of wording: size and thinning control width, not smoothing. Implementation note: send raw input points over the network, which is compact and quantizable, and run getStroke on each client rather than sending outline polygons.
- Sources: https://github.com/steveruizok/perfect-freehand

### Coalesced pointer events: browsers merge several pointer updates into one pointermove, which loses accuracy on fast strokes. getCoalescedEvents() recovers the merged points so curves come out smoother. It is not Baseline: iOS Safari 18.1 and earlier lacks it, Firefox Android always returns an empty array, and iOS 18.2 has a pointerId quirk. It also requires HTTPS. Use e.getCoalescedEvents?.() and fall back to the main event's coordinates when the method is missing or the result is empty.

- Confidence: **high** · Vote: 3-0 (3 merged claims)
- Evidence: MDN: 'user agents coalesce multiple updates into a single event... reduction in the granularity and accuracy when tracking, especially with fast and large movements'; 'Un-coalesced position changes are desirable in drawing applications'; 'This feature is not Baseline because it does not work in some of the most widely-used browsers.' The verifier checked browser-compat-data: Chrome 58+, Firefox desktop 59+, Safari/iOS 18.2+, and Firefox Android marked partial (empty array).
- Sources: https://developer.mozilla.org/docs/Web/API/PointerEvent/getCoalescedEvents

### Preventing scroll and zoom while drawing: set touch-action: none on the canvas before any gesture begins. If the browser takes over a touch gesture, Pointer Events apps get pointercancel and the stroke stops. preventDefault in pointer handlers does not stop panning or zooming, because the browser decides at touch start based on the touch-action already in effect. touch-action does not block ctrl+wheel or trackpad zoom, or a pinch that starts outside the canvas. Many apps add a non-passive touchmove preventDefault as extra protection on iOS.

- Confidence: **high** · Vote: 3-0 (2 merged claims)
- Evidence: MDN: 'none: Disable browser handling of all panning and zooming gestures'; 'An application using Pointer events will receive a pointercancel event when the browser starts handling a touch gesture'; apps 'should also use touch-action to ensure the browser knows the intent of the application before any event listeners have been invoked.' Widely available since September 2019. MDN also warns that touch-action: none can hurt low-vision users who rely on zoom, so limit it to the canvas only.
- Sources: https://developer.mozilla.org/Web/CSS/touch-action

## caveats

Coverage gaps: no verified claims came back for several parts of the question. These are prompt-writing craft and what makes Quiplash prompts funny, exact scoring formulas (points per vote share, the 'Quiplash' sweep bonus), phase timer lengths and pacing benchmarks, Drawful/Fibbage lie-and-guess mechanics, a comparison of Ably, Pusher, Liveblocks, Supabase Realtime and Socket.io (latency, free-tier limits), existing medical party games or trivia apps, guidance on non-stigmatizing medical humor, medical history facts for prompt material (bloodletting, leeches, trepanation, radium, tobacco smoke enemas), and bubbly UI motion, haptics, sound and accessibility. Recommendations in those areas would be design judgment, not verified research. Time sensitivity: the PartyKit shutdown (Oct 2026) matters a great deal, and much of the older tutorial material online that points to hosted PartyKit is now wrong. Durable Object free-tier limits and getCoalescedEvents browser support are both still changing. Source caveats: Jackbox sources are first-party and partly promotional, though they are authoritative for the product's own specs. The zoombombing evidence is one 2020 study of about 200 public attack calls on Zoom-style meetings, and applying it to game lobbies is an inference. The Jackbox moderator URL may have moved from mod.jackboxgames.com to mod.jackbox.tv. Refuted for transparency: the claim that the source docs guarantee same-room-id routing to one instance failed 1-2, even though Cloudflare's idFromName/getByName model works that way in practice. The claim that a unique per-participant link is the only effective defense also failed 1-2, so per-player invite tokens are a reasonable idea but not a proven requirement.

## openQuestions

- What scoring and pacing parameters make Quiplash-style rounds feel best? This covers points per vote percentage, sweep bonuses, the final round format, and answer and vote timer lengths for typing on a phone versus drawing. How should a survival or elimination trivia mode be balanced so that players who are knocked out stay engaged, for example by moving them into the audience?
- What realtime free-tier limits apply in practice to PartyServer on Durable Objects, compared with Ably, Pusher, Liveblocks and Supabase Realtime? Relevant limits are concurrent connections, messages per day, and alarm and storage costs for a game with 8 players plus an audience streaming drawing strokes.
- How should medical-humor prompts be written and screened so the jokes target medicine, training culture, history and wordplay rather than patients or specific conditions? What prior art exists from medical card games or trivia apps?
- Which identity or invite mechanisms (per-player join tokens, host approval queue, device binding) can reliably tell real lobby members from insider-invited trolls without adding friction to quick setup on a phone?
